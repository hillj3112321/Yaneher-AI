# 🚀 Установка Yaneher Community v11 — пошагово

## 0. Не ломаем работающий Yaneher Chat v10

Этот архив **не опубликован** в Netlify, ваш репозиторий **не изменён**. Рекомендуется сначала создать отдельную ветку GitHub и Netlify Deploy Preview, а не обновлять Production сразу. Сохраните копию текущего репозитория и запишите действующий адрес сайта. Старые интерфейсные файлы лежат в `legacy/`.

Внимание: база данных для нового аккаунта обязательна; не размещайте файлы v11 в Production до шага 3. Данные v10, находившиеся в localStorage, не исчезают сами по себе при обновлении, но **привязаны к тому же домену и браузеру**. Если использовали календарь v10, не удаляйте его данные и не очищайте браузер. Кнопка «Импортировать мои записи» в новом календаре пытается перенести локальные записи в аккаунт; перед публикацией экспортируйте старую статистику отдельно, если есть такая возможность. Автоматический перенос не гарантирован для всех версий.

## 1. Создайте реальный Supabase-проект

1. Откройте https://supabase.com/dashboard и создайте новый проект (выберите надёжный отдельный пароль базы).
2. В **SQL Editor → New query** вставьте ВСЁ содержимое `db/INSTALL_ALL.sql` и нажмите **Run**. Это создаёт таблицы, индексы, политику RLS, 5-секундный chat rate limit, серверное ограничение ЯнеИИ в 60 секунд, жалобы и роли. Большая SQL-операция может потребовать лимитов самого SQL Editor.
3. Если `db/supabase.sql` от v10 уже ранее запускался **в этом же проекте Supabase**, не запускайте `INSTALL_ALL.sql`: выполните последовательно `db/v11_upgrade.sql` и `db/seed_lessons.sql`. Сделайте резервную копию базы заранее. Если SQL сообщил об ошибке, не продолжайте настройку до выяснения причины.
4. В **Authentication → Providers → Email** включите Email + password. В **Authentication → URL Configuration** задайте Site URL `https://ВАШ-САЙТ.netlify.app` и разрешённые redirect URLs (включая тестовый адрес). Для устойчивой публичной работы настройте Email SMTP и подтверждение email; бесплатная почтовая отправка Supabase ограничена.
5. Скрипты создают **только** содержание уроков, черновик релиза v1 и технические настройки. Они не создают пользователей, видео, фиктивные отзывы, оплаченные подписки или выдуманные официальные правила.

## 2. Подключите браузер (публичные ключи)

В **Supabase → Project Settings → Data API / API Keys** скопируйте Project URL и **publishable / anon** key. В `site/config.js` заполните:

```js
window.YANE_CONFIG = {
  supabaseUrl: 'https://ВАШ_PROJECT.supabase.co',
  supabaseAnonKey: 'ВАШ_ПУБЛИЧНЫЙ_PUBLISHABLE_ИЛИ_ANON_KEY',
  aiFunction: '/api/yaneai',
  videoWorkerUrl: ''
};
```

**Никогда** не вставляйте в `site/config.js` Gemini API key, Supabase `service_role`/secret key или пароль. Публичный ключ сам по себе не даёт доступ к чужим данным — их защищают RLS-политики. Не отключайте RLS.

## 3. Настройте Netlify и опубликуйте в тестовом окружении

1. В GitHub репозитории `https://github.com/hillj3112321/Yaneher-AI` подготовьте ветку для тестирования и замените исходники файлами v11 с сохранением путей (`site/`, `netlify/functions/`, `netlify.toml`). Не загружайте `.env` с секретами. В существующем Netlify используйте предварительный деплой.
2. В **Netlify → Site configuration → Environment variables** сохраните четыре переменные, доступные функциям: `GEMINI_API_KEY` (ваш действующий секрет), `GEMINI_MODEL` (модель с доступом для ключа, например `gemini-2.5-flash`), `SUPABASE_URL` и `SUPABASE_ANON_KEY`. Существующий работающий ключ Gemini можно использовать повторно. В Netlify Secret values скрывайте секретный ключ. `YANE_AI_ACCESS_CODE` v10 уже не требуется для нового режима.
3. В **Deploys** запустите новый деплой. Дождитесь **Published** (или статус Deploy Preview для тестового окружения).
4. Сайту нужна живая сеть: Supabase JS загружается из CDN. Без Supabase-URL/ключа сайт покажет честное уведомление, вместо фальшивой регистрации и чата.
5. Проверьте регистрацию **двух разных** пользователей, общий чат и жалобу. Проверяйте сначала на тестовом адресе.

## 4. Первый администратор — только владелец

1. На новом сайте зарегистрируйте **свой** аккаунт с email, уникальным ником (3–24 латинских символа, цифр или ` _ `), паролем (от 8 символов), подтверждением пароля.
2. Откройте **Supabase → Authentication → Users**; скопируйте UUID своего пользователя.
3. Откройте Supabase **SQL Editor**, выполните **только для своего UUID** (замените плейсхолдер):

```sql
update public.profiles
set role = 'admin'
where id = 'ВСТАВЬТЕ_UUID_СВОЕГО_АККАУНТА';
```

4. Обновите сайт и снова войдите. Только реальный админ увидит раздел «Управление». Для обычного участника назначить себе роль через браузер нельзя, сервер проверяет права. Не создавайте тестовый публичный админ-аккаунт со стандартным паролем.
5. Для роли **«Основной нарезчик»** найдите пользователя в админке → «Люди» → «Управлять» → «Назначить основным». Эта роль автоматически открывает календарь заработка вместо цели 500К.

## 5. Как работают чат и жалобы

Участник входит, пишет в **Общий чат**; Supabase хранит текст и дату, а Realtime обновляет экран у других. При сообщении есть **«Жалоба»** → причина и комментарий → запись в `chat_reports`. Только админ видит очередь **Управление → Жалобы**, может отклонить, закрыть, удалить сообщение. В **Люди** доступны роли, полный бан, разбан и чат-муты 5/10/30 минут или 7 дней. Все управленческие операции проходят через защищённые серверные RPC. В «Логи» доступен журнал. Админы не получают свободный доступ к истории запросов ЯнеИИ.

5 секунд между сообщениями участников; для админов — без задержки. 60 секунд между запросами ЯнеИИ для каждого аккаунта, на сервере, сохраняется при перезагрузке. Netlify также ограничивает запросы с IP. Лимиты поставщика Gemini и расходы общие для вашего API-ключа — следите за квотой и бюджетом.

## 6. Полный анализ видео и АУДИО — дополнительный сервер

Текстовый Gemini-чат работает через Netlify Functions. **Полное видео нельзя корректно отправлять через небольшую Netlify Function**. Код настоящей обработки лежит в `video-worker/` и запускается ОТДЕЛЬНО на хостинге контейнеров с HTTPS, FFmpeg и Python (Render/Railway/Fly и аналогичные). Dockerfile предоставлен.

Переменные окружения на видеосервере:

- `SUPABASE_URL` — URL того же проекта Supabase.
- `SUPABASE_ANON_KEY` — его public key.
- `GEMINI_API_KEY` — секретный действующий ключ Google.
- `GEMINI_MODEL` — выбранная модель Gemini, поддерживающая видео (и доступная на ключе).
- `ALLOWED_ORIGINS` — **точный** HTTPS origin сайта (например `https://example.netlify.app`), можно несколько через запятую.
- `VIDEO_MAX_MB` — необязательно, по умолчанию 150.
- `VIDEO_MAX_DURATION` — необязательно, по умолчанию 600 секунд.
- `VIDEO_SEGMENT_SECONDS` — необязательно, по умолчанию 120.

В Docker-сервисе порт **8080**; endpoint `POST /analyze` принимает видео (`file`), вопрос (`question`) и язык (`language`) с `Authorization: Bearer SUPABASE_USER_JWT`. **Не открывайте видеосервис публично без HTTPS, авторизации и контроля расходов.**

После публикации видеосервера в `site/config.js` задайте `videoWorkerUrl: 'https://АДРЕС_ВАШЕГО_ВИДЕОСЕРВЕРА'` и заново опубликуйте фронтенд. Тогда вложение MP4/WebM/MOV из ЯнеИИ отправляется на сервер: FFmpeg проверяет всё видео, определяет FPS, вероятные склейки и LUFS/тишину; оригинальный файл со звуком пересылается в Gemini Files API и обрабатывается по последовательным временным интервалам. Модель может самостоятельно выбирать частоту кадров, поэтому **не гарантируется просмотр каждого отдельного кадра моделью**. Исходное видео стирается из временного каталога после обработки; Google Files API может хранить файлы до 48 часов. Без видеосервера вместо ложного анализа будет показана необходимость подключения.

**Ограничения**: 150 МБ и 10 минут на тестовый сервер; на реальном бесплатном тарифе могут быть меньше из-за памяти/времени. Анализ длинного видео занимает ресурсы и может потреблять платную квоту Gemini. Для широкой публичной аудитории понадобятся очереди задач, защита от DDoS, антибот-проверки и бюджетные лимиты.

## 7. Уроки, правила, видео, доход

- **Школа монтажа**: в `db/seed_lessons.sql` есть 14 собственных стартовых пошаговых русскоязычных уроков. Редактор уроков в админке: заголовок, категория, содержание, ссылка на видео, публикация/удаление. Реальные картинки и видеоуроки будут появляться по мере их разрешённого добавления; выдуманных интерфейсных скриншотов нет.
- **Диагностика**: 16 готовых вопросов с полезными пошаговыми ответами и кнопкой перехода в ЯнеИИ.
- **Видео**: пользователи отправляют **HTTPS-ссылку** на оригинал, админ рассматривает/одобряет/отклоняет, после одобрения запись становится видна. Загрузка исходных видеофайлов как общедоступных публикаций ещё НЕ реализована. Максимум 25 подборок задаётся интерфейсом, при этом в базе возможны другие записи. Реальных 25 видео мы не придумывали.
- **Календарь**: cloud `video_stats`, повторный просмотр редактируется у того же видео, 5 000 — порог начислений, 500 000 — цель для пользователей, для «Основного нарезчика» — расчётный доход по $150 за миллион просмотров, дневные/месячные итоги. Курс UAH/RUB берётся из доступного внешнего API; если нет подтверждённого курса, не рисуется выдуманный, а отображаются USD.
- **Правила/баннер**: в базе сначала нет «официальных» текстов, они вводятся администратором после подтверждения. Баннер и URL «вставки» также задаёт админ. Оригинального баннера пользователь пока не передавал — приложенный скриншот **дизайн-концепт, а не самостоятельное изображение для баннера**.
- **Обновления**: v1 создан как **НЕопубликованный** черновик; админ проверяет и публикует после теста. Кнопка карандаша показывает только реально опубликованные обновления.

## 8. Дополнительно: автоматические черновики релизов из GitHub

Необязательно: добавьте в Netlify Environment variables секреты `GITHUB_WEBHOOK_SECRET` (отдельная случайная строка, не Gemini) и `SUPABASE_SERVICE_ROLE_KEY` (**только Netlify secret**, категорически не в `site/config.js`).

В GitHub → Repository → Settings → Webhooks добавьте **Payload URL** `https://ВАШ-САЙТ.netlify.app/api/release-hook`, **Content type** `application/json`, **Secret** тот же `GITHUB_WEBHOOK_SECRET`; выберите событие **Releases**. После каждого GitHub Release код создаёт **неопубликованный** черновик с номером следующей версии и заметками из настоящего GitHub Release. Администратор сначала проверяет запись, затем публикует её через сайт. Сам webhook не меняет публичный changelog без проверки.

## 9. Что уже есть, что ещё не доказано

**Реальный код**: адаптивный UI со светлой/тёмной темой; sidebar; регистрация, роль-модель и RLS; чат + Realtime + жалобы + модерация; профили + ping активности; видео-заявки (по ссылке) и их админ-решения; статистика в базе и импорт из v10; школа и диагностика; подтверждённые правила от администратора; ЯнеИИ с Gemini и per-user rate limit; необязательный сервер полного видео/аудиоанализа; редактируемые релизы и webhook-черновики.

**Требуют реальных внешних ключей и проверки**: публичная регистрация/SMTP, JWT и политики на настоящей Supabase базе, реальная работа Gemini, корректность Realtime при двух пользователях, доступность video-worker по HTTPS. Не проводился тест с живыми Supabase/Gemini, поскольку их секреты и доступ не предоставлены. Без отдельного видео-хостинга полный анализ роликов не включается.

**Не завершено в v11**: 100% перевод всех полей/уроков на UA/EN (часть текстов русская), загрузка видеофайлов в публичную подборку (сейчас ссылки), встроенная отправка push/Telegram о жалобах, отдельное хранение изображений уроков, расширенная очередь/лимиты расходов для массового видеоанализа и полноценный нагрузочный аудит. Функциональность нельзя считать продакшен-готовой до самостоятельного тестового запуска.

Уважайте авторские права на ролики, не публикуйте чужие материалы без разрешения. Для фото и видео предусмотреть согласие на обработку в Gemini; текстовая подсказка о передаче файлов встроена в ЯнеИИ.
